# Separate capture forms own their persistence

The Movements screen carries two parallel capture-form components: the Transaction Form (`QuickAddCardComponent`, which also presents inline on the desktop page and in the mobile bottom sheet) and the Transfer Form (the `#transferForm` template owned by `MovementsComponent`, same dual presentation). A unified capture component discriminated by movement type was considered and rejected: transactions and transfers are structurally separate data models (ADR 0002) with different fields, different validation, and different cross-field state (the Transfer Form's currency-aware exchange-rate capture, ADR 0005). Forcing one component over that seam would buy visual consistency at the cost of a discriminator-driven tangle of conditionals; two components keep each form's complexity in one place.

Each form owns its persistence. The Transaction Form saves through the transaction service, the Transfer Form through the transfer service, and neither reaches into the other's model. Cross-form conveniences that read both models — the shared capture bottom sheet, one-capture-form-at-a-time, cross-form draft restoration, keyboard shortcuts — stay in the Movements page, which composes both forms.

What the two forms share is agreed at the seams, not merged: they render the same Exchange Rate Well and extend the same capture-form style blocks in the shared placeholder library (`src/app/shared/styles/_patterns.scss` — form grid, form actions, rate grid, pinned sheet actions). Where the two forms' styles had drifted, the Transaction Form's look won (the `minmax(0, 1fr)` grid overflow guard and the `--space-md` spacing tokens). Fields resolve to identical rendered widths through `box-sizing: border-box` on the shared `%field` pattern, which fixes the mobile sheet overflow at the root instead of per-form. The styles are one visual grammar; the components remain two.
