# Backup and restore halt on divergence

Before a cloud Backup is saved or a Restore overwrites local data, the two datasets are compared by containment. Every Account, Category, Transaction and Transfer on both sides is reduced to a Content Key — every stored field, the record's own and referenced ids included (ids travel with a record through backups and only diverge when the same record was created independently on two devices), except `active` on Accounts and Categories, which is reversible soft state; duplicates are counted. Keys are computed on normalized records: the backup side is first migrated to the current schema and given the same transforms `overwriteLocalDb` applies (`tags` dropped, `year` derived), dates are compared as ISO strings (local records hold `Date` objects, restored ones hold strings), and fields are serialized in a fixed order with absent and `undefined` treated alike. Profile does not take part in containment — `lastBackupAt` changes on every Backup and Restore — but an identical verdict also requires the same base currency and language.

A side whose records all exist in the other is contained: it loses nothing by being overwritten. A side holding any record the other lacks is divergent.

- Restore: identical data is reported as such and nothing is written; local data contained in the backup (an empty local dataset included — Profile ignored) restores without asking; otherwise the existing confirm warns that the backup is missing data you have locally.
- Backup: a missing cloud file is pushed normally; identical data is reported as already backed up and nothing is uploaded; a cloud backup that matches the Backup Baseline, or is contained in the local data, is replaced silently; local data contained in the cloud (another device is ahead) gets its own message offering Restore instead, Overwrite or Cancel; any other divergence asks before replacing the cloud copy.

Both dialogs show the backup's date and the most recently recorded movement (`createdAt`) on each side. An identical verdict stamps Last Backup with that backup's `exportedAt`.

The Backup Baseline is a fingerprint of the dataset (sorted Content Keys plus base currency and language) of the cloud backup this device last pushed, restored from the cloud, or found identical. It lives in `localStorage` — not in Profile, no `schemaVersion` bump — and is cleared on Erase and on disconnecting the Backup Method; a Restore from a file leaves it untouched. While the cloud still matches it, no other device has replaced the backup, so overwriting it loses nothing this device has not already seen. Without it, every edit or Delete would make the next Backup prompt, since the cloud still holds the old record.

This replaces the previous last-write-wins rule. The data model has no cross-device record identity (ids are device-local auto-increments), no `updatedAt`, and no tombstones, so which side is newer is only knowable at snapshot level. A stored base was first considered for Restore and rejected there: it warns even when the local data is merely older, a false positive that makes users abandon restores, so Restore relies on containment alone, which fires only on real data loss. For Backup the same base is exact — the question is whether the cloud changed since this device last saw it — so Backup consults the Backup Baseline first and falls back to containment when it is missing or stale. Older app versions keep reading and writing compatible backups and simply keep today's behavior; a backup they push no longer matches the Baseline, so the next Backup here falls back to containment.

Rejected alternatives: blind overwrite (silent data loss); automatic merge (needs stable cross-device ids, `updatedAt`, and tombstones to resolve conflicting edits and delete-vs-edit — out of scope; when both sides hold unique data, the user picks a side, with a downloaded backup file as the escape hatch); matching records by id to ignore edits (cannot tell which side made the edit, so another device's edit would be lost silently); per-table detail in the dialogs (pluralization across languages is harder to maintain than the binary message plus the date lines).

Consequences: Backup always downloads the cloud file before pushing (one extra GET; a missing file means there is nothing to overwrite). Backup's confirm is shared by the sidebar action, the mobile top-bar quick action and the Settings backup card, and a confirmed overwrite reuses the verdict already computed instead of checking again. Builds on ADR-0004 and ADR-0006; amends the last-write-wins line in docs/spec.md.
