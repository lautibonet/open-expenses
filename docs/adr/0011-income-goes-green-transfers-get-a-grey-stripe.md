# 0011 - Income goes green; transfers get a grey stripe (D8 reversal)

The D8 "no green token" decision (ADR 0010) traded income distinctness for palette economy: income read in the same blue family as every interactive element, and transfers in the Movements table had no edge signal at all — only a background tint. In practice the blue-as-income / blue-as-action ambiguity was the migration plan's own listed risk (MIGRATION.md §6, risk 7, "revisit later"), and the glossary (`CONTEXT.md`) never adopted the blue scheme: it still described stripes-as-type-signal with green for Income, red for Expense, grey for Transfer.

We reverse D8: a single **Income** token (`--income: #15803d`, the retired ledger green, dark enough for WCAG AA at the amount's type size) colors income amount text, the income directional stripe (`--stripe-income`), the Stats Avg Income card stripe, and the Net Flow card's IN line. Transfers gain a quiet grey stripe token (`--stripe-transfer: 4px solid var(--outline)`). Expense stays Error red. Because the stripe now carries the full type signal, the Movements table's Type column is dropped — the ↑/↓/= arrows disappear with it — and month group header rows span the reduced column count. Blue is unambiguously action/information again, and green means money in and nothing else.

Consequences: every consumer of `--stripe-income` (Movements rows, KPI cards, Net Flow card, Settings category chips) turns green by token substitution; green is never used for interactive elements; and the design docs (`DESIGN.md`, `MIGRATION.md` D8 row) record the reversal in step rather than deleting the prior decision.
